# User Stories (MasterMeister5)

内訳方式: Epic-Based（`requirements.md` 4.1〜4.5に対応）＋ Persona-Basedのハイブリッド。
粒度: 細かい粒度（1ストーリー＝1操作）。受け入れ基準: Given/When/Then形式。
ペルソナ: [personas.md](personas.md) の「管理者」「一般ユーザ」の2種類。

各ストーリーはINVEST基準（独立・交渉可能・価値がある・見積可能・小さい・テスト可能）を満たす
ことを意図して作成している。

---

## Epic 1: ユーザ登録・認証（requirements.md 4.1）

### US-1.0（管理者）初期管理者アカウントでログインする
**As a** 管理者
**I want** 環境変数等で指定された初期管理者アカウントでログインする
**So that** ユーザが一人も存在しない初期状態からシステムのセットアップを開始できる

**Acceptance Criteria**
- Given システムが初めて起動され、管理者アカウントが1件も存在しない
- When 起動時に環境変数等で指定された初期管理者アカウントの認証情報でログインする
- Then 通常の招待フローを経ずにログインでき、管理者としてすべての管理機能にアクセスできる

### US-1.1（管理者）ユーザを招待する
**As a** 管理者
**I want** メールアドレスとロールを指定してユーザを招待する
**So that** 新しいユーザにシステムの利用を開始してもらえる

**Acceptance Criteria**
- Given 管理者としてログインしている
- When 未登録のメールアドレスとロール（管理者／一般ユーザ）を指定して招待する
- Then 有効期限付きの招待リンクを含むメールが対象アドレスに送信され、招待済み・未完了状態のユーザとして記録される
- Given 既に本登録完了済みのメールアドレスを指定した
- When 招待を実行しようとする
- Then エラーとして拒否され、登録済みである旨が管理者に明示される
- Given 招待済み・未完了のメールアドレスを指定した
- When 招待を実行しようとする（再送操作ではない通常の招待操作）
- Then 招待メールは自動再送されない

### US-1.2（管理者）招待を再送する
**As a** 管理者
**I want** 招待済み・未完了のユーザに招待メールを再送する
**So that** メール未達やリンク期限切れの際に再度案内できる

**Acceptance Criteria**
- Given 招待済み・未完了のユーザが存在する
- When 管理者が明示的に「招待再送」操作を行う
- Then 新しい有効期限の招待メールが再送される

### US-1.3（管理者）ユーザのロールを設定・変更する
**As a** 管理者
**I want** ユーザのロール（管理者／一般ユーザ）を設定・変更する
**So that** 業務内容の変化に応じて適切な権限区分を維持できる

**Acceptance Criteria**
- Given 招待時にロールを指定する
- When 招待を作成する
- Then 指定したロールが招待済みユーザに設定される
- Given 本登録完了済みのユーザが存在する
- When 管理者がロールを別のロールへ変更する
- Then 変更が即座に反映され、元のロールへ戻すことも可能である

### US-1.4（管理者）ユーザを無効化する
**As a** 管理者
**I want** ユーザアカウントを無効化する
**So that** 退社・異動等でアクセス権を失わせるべきユーザのログインを止められる

**Acceptance Criteria**
- Given 本登録完了済みのユーザが存在する
- When 管理者がそのユーザを無効化する
- Then ユーザは以降ログインできなくなる
- Given 無効化されたユーザが既存のログインセッション（有効なアクセストークン）を持っている
- When 無効化後にAPIへアクセスする
- Then 認可判定の詳細（即時失効か、トークン有効期限切れまで有効か）はFunctional Designで確定する

### US-1.5（管理者）ユーザを再有効化する
**As a** 管理者
**I want** 無効化したユーザを再有効化する
**So that** 誤って無効化した場合や、休職からの復職等に対応できる

**Acceptance Criteria**
- Given 無効化されたユーザが存在する
- When 管理者がそのユーザを再有効化する
- Then ユーザは再びログイン可能になる

### US-1.6（一般ユーザ）招待メールから本登録を完了する
**As a** 招待された一般ユーザ
**I want** 招待メールのリンクから氏名とパスワードを設定して本登録を完了する
**So that** システムにログインして業務を開始できる

**Acceptance Criteria**
- Given 有効期限内の招待リンクを受け取っている
- When リンクから氏名等のユーザ情報とパスワード（ポリシーを満たすもの）を設定する
- Then 本登録が完了し、追加の承認ステップなしに即座にログイン可能になる
- Given 招待リンクの有効期限（デフォルト3時間）が切れている
- When リンクにアクセスする
- Then 本登録は失敗し、管理者による招待再送が必要である旨が案内される

### US-1.7（一般ユーザ）ログインする
**As a** 登録済みユーザ
**I want** メールアドレスとパスワードでログインする
**So that** 権限範囲内の機能を利用できる

**Acceptance Criteria**
- Given 有効なアカウントと正しい認証情報を持っている
- When ログインする
- Then アクセストークン（デフォルト10分）とリフレッシュトークン（デフォルト24時間）が発行される
- Given 同一ユーザが複数端末・複数ブラウザから同時にログインする
- When それぞれの端末でログインする
- Then 制限なく多重ログインが許可される
- Given 同一アカウントへのログイン失敗が設定回数（デフォルト5回）連続した
- When さらにログインを試みる
- Then アカウントが設定時間（デフォルト15分）ロックされ、時間経過により自動的に解除される（管理者による手動解除はない）
- Given 使用済みとして無効化されたリフレッシュトークンが再度提示された
- When トークンリフレッシュが試みられる
- Then トークン窃取・再送の兆候とみなし、同じトークンファミリに属する全トークンが一括で失効する

### US-1.8（一般ユーザ）ログアウトする
**As a** ログイン中のユーザ
**I want** ログアウトする
**So that** 使用中の端末でのセッションを終了できる

**Acceptance Criteria**
- Given ログイン中で有効なリフレッシュトークンを保持している
- When ログアウトAPIを呼び出す
- Then サーバ側でそのリフレッシュトークンが即座に失効する
- Given 同一ユーザが他端末でも多重ログイン中である
- When 一端末でログアウトする
- Then 他端末のセッション（リフレッシュトークン）には影響しない

### US-1.9（一般ユーザ）パスワードをリセットする
**As a** パスワードを忘れたユーザ
**I want** メールアドレス宛のリンクから新しいパスワードを設定する
**So that** パスワードを忘れても自力でログインを再開できる

**Acceptance Criteria**
- Given 登録済みのメールアドレスを持っている
- When パスワードリセットを申請する
- Then リセットリンク付きのメールが送信される
- Given 有効期限内のリセットリンクを受け取っている
- When リンクから新しいパスワード（ポリシーを満たすもの）を設定する
- Then パスワードが更新され、新しいパスワードでログイン可能になる
- 詳細な有効期限のデフォルト値・無効化ユーザに対する挙動はFunctional Designで確定する

### US-1.10（一般ユーザ）パスワードを変更する
**As a** ログイン中のユーザ
**I want** 現在のパスワードを確認したうえで新しいパスワードに変更する
**So that** 定期的にパスワードを更新してアカウントの安全性を高められる

**Acceptance Criteria**
- Given ログイン中である
- When 現在のパスワードと、ポリシーを満たす新しいパスワードを入力して変更を申請する
- Then パスワードが更新される
- Given 現在のパスワードの入力が誤っている
- When 変更を申請する
- Then エラーとなり、パスワードは変更されない

## Epic 2: 対象RDBMSセットアップ・アクセス制御（requirements.md 4.2）

### US-2.1（管理者）対象RDBMS接続を登録する
**As a** 管理者
**I want** 対象RDBMSへの接続情報を登録する
**So that** そのデータベースをマスタメンテナンス・クエリ機能の対象にできる

**Acceptance Criteria**
- Given 対象RDBMS（MySQL/MariaDB/PostgreSQL/H2）への接続情報を持っている
- When 管理者が接続情報を登録する
- Then 独立したIDを持つ接続として登録され、接続パスワードは内部DBに可逆暗号化して保存される

### US-2.2（管理者）対象RDBMS接続を無効化する
**As a** 管理者
**I want** 使わなくなった対象RDBMS接続を無効化する
**So that** 誤操作を防ぎつつ、過去の権限設定・クエリ履歴・監査ログを保持できる

**Acceptance Criteria**
- Given 有効な接続が存在する
- When 管理者がその接続を無効化する
- Then 接続は一覧上で非表示または区別表示され、新規のスキーマ再取込・クエリ実行等の操作が不可になる
- Then 紐づく権限設定・カスタマイズ定義・保存クエリ・クエリ実行履歴・監査ログはすべて保持され続ける（物理削除は提供しない）

### US-2.3（管理者）スキーマを取り込む
**As a** 管理者
**I want** 対象RDBMSのテーブル/ビュー構造を取り込む
**So that** アクセス権限設定・マスタメンテナンス機能の対象スキーマ情報を最新化できる

**Acceptance Criteria**
- Given 有効な対象RDBMS接続が登録されている
- When スキーマ更新操作を実行する
- Then 対象RDBMSに接続し、テーブル/ビュー構造（物理名、コメント、型、制約）が読み取られ内部DBに取り込まれる
- Given 既存のカスタマイズ定義が、再取込後に存在しなくなったカラム・テーブルを参照している
- When 再取込が完了する
- Then 該当のカスタマイズ定義エントリは自動的に削除され、削除件数のサマリが再取込結果画面に表示される

### US-2.4（管理者）アクセス権限（主権限・補助権限）を設定する
**As a** 管理者
**I want** スキーマ／テーブル／カラムの各階層に主権限・補助権限を設定する
**So that** ユーザ・グループごとに適切なデータアクセス範囲を制御できる

**Acceptance Criteria**
- Given スキーマ／テーブル／カラムの各階層に主権限（NONE/READ/UPDATE）を設定できる
- When より詳細な階層（カラム）に設定がある
- Then カラム＞テーブル＞スキーマの優先順位で実効的な主権限が決まる
- Given スキーマ／テーブル単位に補助権限（CREATE/DELETE）を設定できる
- When ユーザが所属する複数グループにそれぞれ権限設定がある
- Then より許可的な方（主権限は上位、補助権限はOR）で合成され、ユーザ個別の明示的な設定はグループの合成結果より常に優先される
- Given 権限設定・グループ構成・スキーマ再取込のいずれかが変更された
- When 変更が確定する
- Then 実効権限のキャッシュ（Caffeine）が無効化される

### US-2.5（管理者）アクセス権限設定をYAMLでエクスポートする
**As a** 管理者
**I want** 特定の対象RDBMS接続のアクセス権限設定をYAML形式でエクスポートする
**So that** レビュー・バックアップ・他環境への複製に利用できる

**Acceptance Criteria**
- Given 対象接続にアクセス権限設定が存在する
- When エクスポートを実行する
- Then 現在の権限設定がYAML形式でダウンロードできる

### US-2.6（管理者）アクセス権限設定をYAMLでインポートする
**As a** 管理者
**I want** YAMLファイルからアクセス権限設定を一括投入する
**So that** 大量の設定を効率的に反映できる

**Acceptance Criteria**
- Given 対象接続向けのYAMLファイルを用意している
- When インポートを実行する
- Then 対象接続の既存の権限設定がすべて削除されたうえで、YAMLの内容から再構築される（全置換、マージではない）
- Given YAML内に重複エントリが存在する
- When インポートを実行する
- Then インポート全体が拒否され、部分的な適用は行われない（トランザクション単位）

### US-2.7（管理者）ユーザグループを管理する
**As a** 管理者
**I want** ユーザグループの作成・改名・削除、およびグループへのユーザ追加・削除を行う
**So that** 部署やチーム単位でアクセス権限をまとめて管理できる

**Acceptance Criteria**
- Given グループを作成・改名できる
- When 管理者が操作する
- Then 変更が即座に反映される
- Given グループを削除する
- When 削除を実行する
- Then 所属関係および当該グループに設定されている権限もあわせて削除される（カスケード）
- Given グループへユーザを追加・削除できる
- When 管理者が操作する
- Then アクセス権限はユーザ個別またはグループ単位のいずれでも設定できる状態を維持する

## Epic 3: マスタメンテナンス機能（requirements.md 4.3）

### US-3.1（一般ユーザ）テーブル/ビュー一覧とレコード一覧を表示する
**As a** 一般ユーザ
**I want** 権限範囲内のテーブル/ビュー一覧と、ページング付きのレコード一覧を表示する
**So that** 対象データの現状を確認できる

**Acceptance Criteria**
- Given 読み取り権限以上を持つテーブル/ビューが存在する
- When 一覧画面を開く
- Then それらのテーブル/ビューがページング付きレコード一覧として表示される
- Then 読み取り権限のないカラムは一覧に表示されない

### US-3.2（一般ユーザ）レコードをフィルタ・ソートする
**As a** 一般ユーザ
**I want** 読み取り権限のあるカラムを対象にフィルタ条件・ソートを指定する
**So that** 必要なデータだけを素早く絞り込める

**Acceptance Criteria**
- Given 読み取り権限のあるカラムが存在する
- When UIでフィルタ条件・ソート順を指定する
- Then 条件に合致するレコードのみが表示される

### US-3.3（一般ユーザ）WHERE句・ORDER BY句を手入力する
**As a** SQLに詳しい一般ユーザ
**I want** WHERE句・ORDER BY句を直接入力する
**So that** UIでは表現しづらい複雑な条件で絞り込める

**Acceptance Criteria**
- Given 一覧画面を開いている
- When WHERE句・ORDER BY句を手入力する
- Then 権限の有無に関係なく指定した条件でレコードが絞り込まれる（表示自体は権限のある列に限定される）

### US-3.4（一般ユーザ）レコードを編集して一括反映する
**As a** 一般ユーザ
**I want** 更新権限のあるカラムの値を編集し、「反映」ボタンで一括送信する
**So that** 複数件の変更をまとめて安全に確定できる

**Acceptance Criteria**
- Given 更新権限のあるカラムを一覧上で編集している
- When 「反映」ボタンを押下する
- Then 変更内容が単一トランザクションとしてバックエンドAPIに送信される
- Given バッチ中の1件でも権限チェックまたは制約チェックに失敗する
- When 反映を実行する
- Then 全体が反映されずDBへの変更はゼロ件となる（オールオアナッシング）

### US-3.5（一般ユーザ）レコードを作成する
**As a** 一般ユーザ
**I want** 新しいレコードを作成する
**So that** 必要なマスタデータを追加できる

**Acceptance Criteria**
- Given `CREATE`補助権限があり、かつ（主キーを持たないテーブル、または全主キー列がUPDATE以上）である
- When レコード作成を実行する
- Then 作成が成功する
- Given 上記条件を満たさない
- When レコード作成を試みる
- Then 作成は拒否される

### US-3.6（一般ユーザ）レコードを削除する
**As a** 一般ユーザ
**I want** 不要になったレコードを削除する
**So that** マスタデータを最新の状態に保てる

**Acceptance Criteria**
- Given `DELETE`補助権限があり、かつ主キーを持ち、かつ全主キー列がREAD以上である
- When レコード削除を実行する
- Then 削除が成功する
- Given 主キーを持たないテーブルである
- When 削除を試みる
- Then 常に削除は拒否される

### US-3.7（管理者）表示・入力カスタマイズ定義をYAMLで管理する
**As a** 管理者
**I want** 対象RDBMS接続ごとのマスタメンテナンス画面のカスタマイズ定義（表示ラベル・列順・
初期ソート・入力ウィジェット種別・非表示/読取専用化・簡易バリデーション）をYAMLでアップロード
/ダウンロードする
**So that** 業務担当者が使いやすい画面に調整できる

**Acceptance Criteria**
- Given カスタマイズ定義をYAML形式で用意している
- When 管理者ダッシュボードからアップロードする
- Then 対象接続のカスタマイズ定義として適用される
- Given カスタマイズ定義がREAD権限のない列を「表示」に設定している
- When マスタメンテナンス画面が表示される
- Then アクセス権限モデルが優先され、その列は非表示のままとなる（カスタマイズ定義は権限を上書きしない）

## Epic 4: クエリ関連機能（requirements.md 4.4）

### US-4.1（一般ユーザ）クエリビルダーでSQLを組み立てる
**As a** SQLの知識がない一般ユーザ
**I want** タブ構成（SELECT/FROM/JOIN/WHERE/GROUP BY/HAVING/ORDER BY/LIMIT OFFSET）のUIでSQLを組み立てる
**So that** SQLを直接書かずに必要なデータ抽出を行える

**Acceptance Criteria**
- Given クエリビルダー画面を開いている
- When 各タブでUI操作を行う
- Then スキーマ非修飾のSQL（対象スキーマは実行時に指定）が生成される

### US-4.2（一般ユーザ）既存のSQLをクエリビルダーに反映する
**As a** 一般ユーザ
**I want** 手入力または保存済みのSQLをクエリビルダーの各タブに逆変換して表示する
**So that** 既存のクエリをベースに条件を調整できる

**Acceptance Criteria**
- Given 他機能（保存クエリ、手入力SQL）からクエリビルダーへ遷移する
- When 遷移が行われる
- Then SQLが解析され、対応する各タブに条件が反映される

### US-4.3（一般ユーザ）クエリを保存する
**As a** 一般ユーザ
**I want** 作成したSQLに名前を付けて保存し、公開/非公開を選択する
**So that** 繰り返し使うクエリを再利用できる

**Acceptance Criteria**
- Given 手入力またはクエリビルダーで作成したSQLがある
- When 名前と公開/非公開区分を指定して保存する
- Then クエリが保存される（スキーマは保持しない）
- Given 自分が作成したクエリではない
- When 編集を試みる
- Then 編集は拒否される（編集は作成者のみ可能）

### US-4.4（一般ユーザ）保存クエリを論理的に非表示にする
**As a** クエリの作成者
**I want** 使わなくなった保存クエリを論理的に非表示（retired）にする
**So that** 一覧を整理しつつ、実行履歴の参照整合性を保てる

**Acceptance Criteria**
- Given 自分が作成した保存クエリが存在する
- When retired状態に変更する
- Then 一覧から非表示になるが、過去のクエリ履歴上の参照は保たれる

### US-4.5（一般ユーザ）クエリを実行する
**As a** 一般ユーザ
**I want** 保存クエリまたは直接入力したSQLを、対象スキーマを指定して実行する
**So that** 必要なデータを取得できる

**Acceptance Criteria**
- Given 読み取り専用のSQLと、許可リストに含まれる対象スキーマを指定している
- When 実行する
- Then クエリが実行され、SQL・パラメータ・対象スキーマ・結果件数・実行時間・実行回数・実行日時・実行者が記録される
- Given `:param`形式のパラメータを含むSQLである
- When 実行画面を開く
- Then パラメータが自動検出され、値設定UIが提示される
- Given 保存クエリを実行しようとしている
- When 実行画面を開く
- Then SQL自体は編集不可として表示される
- Given 更新・削除等の読み取り専用でないSQLである
- When 実行を試みる
- Then 実行は拒否される

### US-4.6（一般ユーザ）クエリ履歴を閲覧する
**As a** 一般ユーザまたは管理者
**I want** クエリ実行履歴をページング付きで閲覧し、実行日時・実行者・対象スキーマ・SQLテキストで絞り込む
**So that** 過去の実行内容を追跡・再確認できる

**Acceptance Criteria**
- Given クエリ実行履歴が存在する
- When 履歴画面を開く
- Then 保存クエリと直接入力クエリを区別した一覧がページング付きで表示される
- When 実行日時・実行者・対象スキーマ・SQLテキストで絞り込む
- Then 条件に合致する履歴のみが表示される

## Epic 5: 監査ログ（requirements.md 4.5）

### US-5.1（管理者）監査ログを閲覧する
**As a** 管理者
**I want** 認証イベント・管理操作・データアクセスイベントの監査ログを閲覧する
**So that** システムの利用状況・異常の兆候を把握できる

**Acceptance Criteria**
- Given ログイン・ログアウト・ログイン失敗、ユーザ招待・ロール変更・アカウント無効化/再有効化、
  対象RDBMS接続設定の変更、スキーマ取込操作とその結果、アクセス権限設定の変更（グループ変更・
  権限設定変更・YAMLエクスポート・YAMLインポートを区別）、大量データ取得（デフォルト100件以上）、
  クエリ実行、データ更新操作（挿入・更新・削除）が発生している
- When 管理者が監査ログ画面を開く
- Then それぞれのイベントが日時（ISO 8601）・ユーザID・対象接続ID・操作種別・対象リソース・
  結果ステータスとともに一覧表示される
- Given 一般ユーザとしてログインしている
- When 監査ログ画面へのアクセスを試みる
- Then アクセスは拒否される（管理者のみ閲覧可能）
