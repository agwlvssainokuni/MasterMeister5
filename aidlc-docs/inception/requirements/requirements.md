# Requirements: MasterMeister5

## 1. Intent Analysis Summary

- **User Request**: 新規にRDBMSマスタメンテナンスアプリケーション「MasterMeister5」を開発する。
  既存プロダクトMasterMeister4を踏襲しつつ、いくつかの変更・追加を加えた後継プロダクトとして
  greenfieldで開発する。要件一式は `reference/aidlc-requirements-input/` にフルスペックで
  事前投入されている。
- **Request Type**: New Project（新規プロジェクト）
- **Initial Scope Estimate**: System-wide（認証・アクセス制御・マスタメンテナンス・クエリ機能・
  監査ログ・UIデザインシステム基盤など、複数の機能ブロックにまたがる）
- **Initial Complexity Estimate**: Complex（多階層権限モデルの合成ロジック、YAML入出力、
  SQL動的生成、JWTトークン管理など、業務ロジック・非機能要件ともに複雑度が高い）
- **Requirements Depth**: Comprehensive

## 2. プロジェクト概要・スコープ

### 開発体制・優先順位
- 単独開発者による初期開発。MVPファーストで段階的に機能を追加する。
- 優先順位: デザインシステム基盤（`make-you-chic-ui`組み込み・テーマ確定・共通レイアウト確定）
  → ユーザ管理 → 対象RDBMSセットアップ → アクセス制御 → データ表示 → その他機能

### 対象に含める範囲
- ユーザ登録・認証（管理者招待制）
- 対象RDBMSセットアップ・アクセス制御（複数接続、多階層権限モデル、YAML入出力、グループ管理）
- マスタメンテナンス（一覧・絞込・編集・作成・削除、表示・入力カスタマイズ）
- クエリビルダー・クエリ保存・クエリ実行・クエリ履歴
- 監査ログ閲覧

### 明示的に対象外とする範囲
- 招待用パス・トークンパラメータ名のカスタマイズ
- 監査ログへのIPアドレス記録
- ログアウト時のセッション継続時間記録
- 監査ログの保持期間設定・自動削除（パージ）機能
- レジリエンシーベースライン（可用性・DR等の設計時ベストプラクティス）
- モバイルデバイスへの本格対応（レスポンシブの範囲内でのみ配慮、デスクトップ中心）
- CI/CDパイプラインの構築は開発の最終段階に後回し

### MasterMeister4からの主な変更点
- **ユーザ登録フロー**: 自己申告制 → 管理者による招待制に変更
- **UIコンポーネントライブラリ**: 独自CSS/コンポーネントのゼロ構築 → 自前のデザインシステム
  ライブラリ`make-you-chic-ui`の組み込みに変更
- **メールテンプレートエンジン**: 自作Mustacheエンジン（`cherry-mustache-core`） → 外部公開
  ライブラリ`java-mustache-processor`の利用に変更
- **マスタメンテナンス機能のカスタマイズ**: [追加] 対象RDBMS接続ごとのYAML定義ファイルによる
  表示・入力カスタマイズに対応
- 上記以外は技術スタック・アクセス制御モデル・クエリ関連機能・監査ログ・非機能要件を含め
  MasterMeister4を踏襲する

## 4. 機能要件

### 4.1 ユーザ登録・認証

#### 登録フロー
1. 管理者が管理者ダッシュボードでユーザのメールアドレスを登録する（一般ユーザからの登録申請は
   受け付けない）
2. 登録と同時に、管理者はそのユーザのロールを設定する
3. 登録すると、対象メールアドレス宛に有効期限付きリンクを含む招待メールが送信される
4. ユーザは招待メール内のリンクから、氏名等のユーザ情報とパスワードを設定し、登録を完了する
5. 登録完了と同時に本登録済みとなり、ログイン可能になる（別途の管理者承認ステップは発生しない）

管理者承認ワークフロー（自己申告制の承認/却下フロー）は持たない。

#### ロール設定
- 管理者はメールアドレス登録（招待）時に、そのユーザのロールを設定できる
- 正式登録完了後も、管理者はユーザのロールを変更できる（双方向に変更自由）
- ロールの種類: 管理者／一般ユーザの2種類

#### アカウント無効化・再有効化 **[要件確認Q3で追加確定]**
- 管理者はユーザを無効化できる。無効化されたユーザはログイン不可になる
- 管理者は無効化されたユーザを再有効化できる（双方向）
- 無効化はロール設定とは独立した状態として管理する

#### セキュリティ対策
- メールアドレス列挙攻撃対策: 撤廃する。登録エンドポイントを叩くのは認証済み管理者のみと
  なるため。管理者には登録済みかどうかを明確に返す
- **招待済みメールアドレスへの重複登録**: 状態に応じて挙動を分ける
  - 既に本登録完了済みのメールアドレス → エラーとして拒否する
  - 招待済み・未完了 → 重複登録操作では自動再送しない。管理者が明示的に「招待再送」操作を
    選んだ場合のみ再送する
- 招待トークンの有効期限: 設定可能とする（デフォルト3時間）
- **パスワードポリシー**: 最小文字数のみを要件とする（例: 8文字以上）。文字種混在等の複雑さ
  要件は課さない。security-baseline拡張に基づき、既知の漏洩パスワードリストとの照合チェックを
  行う。パスワードは適応型ハッシュアルゴリズム（bcrypt、Argon2等）でハッシュ化して保存する
- **ログイン試行回数制限・アカウントロック**: 同一アカウントへのログイン失敗が一定回数連続した
  場合、アカウントを一定時間ロックする。回数・ロック時間はいずれも設定可能（デフォルト5回連続
  失敗／15分ロック）。管理者による手動解除は持たず、ロック時間の経過により自動的に解除される

#### パスワードリセット（忘れた場合の再設定） **[要件確認Q1で追加確定]**
- ユーザがパスワードを忘れた場合、招待フローと同様の仕組みでパスワードを再設定できる
- ユーザがメールアドレスを入力するとリセットリンク付きメールが送信され、リンクから新しい
  パスワードを設定する
- リセットトークンの有効期限は招待トークンと同様に設定可能とする（デフォルト値は招待
  トークンに準じる。詳細はFunctional Designで確定）
- 無効化されたユーザに対するパスワードリセットの可否はFunctional Designで確定する

#### パスワード変更（ログイン中ユーザの自己変更） **[要件確認Q2で追加確定]**
- ログイン中ユーザは、現在のパスワードを確認したうえで新しいパスワードに変更できる
- パスワードポリシー（最小文字数、漏洩パスワードリスト照合）は登録時と同様に適用する

#### 初期管理者アカウント
アプリ起動時に環境変数等で指定した最初の管理者アカウントを自動作成する仕組みが必要
（通常の招待フローを経ない、初期セットアップ専用の仕組み）。

#### 認証トークン
- アクセストークンの方式・有効期限: ステートレスJWT。有効期限設定可能（デフォルト10分）
- リフレッシュトークンの方式・有効期限・ローテーション方式: 内部DBに永続化（ハッシュ化して
  保存、平文は保持しない）。有効期限設定可能（デフォルト24時間）。リフレッシュのたびに新しい
  リフレッシュトークンを発行し、使用済みの旧トークンは無効化する（1回限り使用可能）
- 再利用検知: 要。使用済みとして無効化されたトークンが再度提示された場合、トークン窃取・
  再送の兆候とみなし、同じトークンファミリに属する全トークンを一括で失効させる
- **同一ユーザの多重ログイン許可**: 許可する（同一ユーザの複数端末・複数ブラウザからの同時
  ログインを制限なく許可）
- **ログアウト時のリフレッシュトークン失効 [要件確認Q4で追加確定]**: ログアウトAPI呼び出し時に、
  そのリフレッシュトークンをサーバ側で即座に失効させる（security-baseline拡張SECURITY-12の
  「セッションはログアウト時に無効化される」要件に対応。多重ログイン中の他端末のトークンには
  影響しない）

### 4.2 対象RDBMSセットアップ・アクセス制御

#### 接続管理
管理者が管理者ダッシュボードで対象RDBMSの接続情報を登録する。接続は複数登録でき、それぞれ
独立したIDを持つ。取込内容・権限設定・監査ログはすべて接続IDに紐づけて管理する。

#### 接続の削除 **[要件確認Q5で追加確定]**
対象RDBMS接続は**物理削除を提供しない**。接続は論理削除（無効化）のみ可能とする。無効化された
接続は一覧上で非表示または区別表示されるが、紐づく権限設定・カスタマイズ定義・保存クエリ・
クエリ実行履歴・監査ログはすべて保持され続ける（物理削除がないため、カスケード削除やデータ
保全の問題自体が発生しない）。無効化された接続への新規操作（スキーマ再取込、クエリ実行等）は
不可とする。再有効化の要否はFunctional Designで確定する。

#### スキーマ取込
スキーマ更新操作により対象RDBMSに接続し、テーブル/ビュー構造（物理名、コメント、型、制約）を
読み取り内部DBに取り込む。

#### アクセス権限モデル
主権限（読み書きレベル）と補助権限（作成・削除の可否）を分離して管理する。

- **主権限**: スキーマ／テーブル／カラムの各階層に設定可能な3値（`NONE`/`READ`/`UPDATE`）。
  より詳細な階層（カラム＞テーブル＞スキーマ）の設定が優先する
- **補助権限**: スキーマ／テーブル単位に設定する独立した真偽値（`CREATE`/`DELETE`）
- **レコード作成可否**: `CREATE`補助権限が付与されており、かつ（主キーを持たないテーブル、
  または全主キー列が`UPDATE`以上）の場合に可能
- **レコード削除可否**: `DELETE`補助権限が付与されており、かつ主キーを持ち、かつ全主キー列が
  `READ`以上の場合に可能。主キーを持たないテーブルは常に削除不可
- **グループとの合成**: ユーザが所属する各グループについて同じロジックで実効権限を算出し、
  より許可的な方（主権限は上位、補助権限はOR）で合成する。ユーザ自身の明示的な個別設定は
  グループの合成結果より常に優先する
- **実効権限のキャッシュ**: 算出結果はキャッシュする（Caffeine）。権限設定の変更、グループ
  構成の変更、スキーマ再取込のいずれかが発生した場合はキャッシュを無効化する

#### エクスポート・インポート
YAML形式でエクスポート／インポート可能とする。インポートは全置換方式とする（対象接続の
既存の権限設定をすべて削除したうえで、YAMLの内容から再構築する）。YAML内に重複エントリが
存在する場合はインポート全体を拒否し、部分的な適用は行わない（トランザクション単位で処理）。

#### グループ管理
管理者はユーザグループを作成・改名・削除できる。削除時は所属関係および当該グループに設定
されている権限もあわせて削除する（カスケード）。管理者はグループへのユーザ追加・削除を行える。
アクセス権限はユーザ個別またはグループ単位のいずれでも設定できる。

### 4.3 マスタメンテナンス機能

- テーブル/ビュー一覧、ページング付きレコード一覧を表示する
- 読み取り権限以上を持つカラムのみを対象に、フィルタ条件・ソートを直感的なUIで指定可能とする
- WHERE句・ORDER BY句の手入力（権限に関係なく利用可能）にも対応する
- レコード一覧画面上で、更新権限のあるカラムの値を編集できる
- 「反映」ボタン押下で、変更内容を単一トランザクションとしてバックエンドAPIに送信する。
  バッチ中の1件でも権限チェックまたは制約チェックに失敗した場合は、全体を反映せずDBへの
  変更をゼロ件とする（オールオアナッシング）
- `CREATE`補助権限がある場合はレコード作成、`DELETE`補助権限がある場合はレコード削除が可能
- 作成・更新・削除のすべての操作を単一トランザクションとして扱うAPIエンドポイントに統合する

#### 表示・入力カスタマイズ
- **カスタマイズ可能な項目**:
  - 表示ラベル（物理カラム名に代わる論理名）、一覧での列の並び順、デフォルトのソート順
  - 入力ウィジェット種別（例: セレクトボックス（固定値リスト）、チェックボックス、日付ピッカー等。
    型からの自動判定を上書きする）
  - 列の非表示化・読取専用化（一覧・編集画面上で意図的に隠す、または常に読取専用にする）
  - 簡易バリデーションルールの追加（正規表現、値の範囲等。DB制約に加えて定義ファイル側で
    追加のチェックを指定できる）
- **定義ファイルの形式・管理**: YAML形式。既存の権限設定YAMLエクスポート/インポートと同様、
  管理者ダッシュボードの画面からYAMLを直接アップロード/ダウンロードして編集する
- **適用単位**: 対象RDBMS接続ごと。同じテーブル名でも接続が異なれば別々の定義を持てる
- **スキーマ再取込との整合性**: スキーマ再取込のたびに、存在しなくなったカラム・テーブルを
  参照するカスタマイズ定義エントリを自動的に削除する（エラーにはせず、定義ファイルが陳腐化
  したまま残らないようにする）。再取込結果画面に「削除されたカスタマイズ定義: N件」等の
  サマリを表示し、管理者に通知する
- **権限との関係**: カスタマイズ定義は表示・入力の調整に留まり、アクセス権限モデル（主権限・
  補助権限）による制御を上書きしない。READ権限がない列はカスタマイズ定義に関わらず非表示のまま

### 4.4 クエリ関連機能（ビルダー・保存・実行・履歴）

- **クエリビルダー**: タブ構成（SELECT/FROM/JOIN/WHERE/GROUP BY/HAVING/ORDER BY/LIMIT OFFSET）。
  UIでの指定内容からスキーマ非修飾のSQLを生成する（対象スキーマは実行時に指定）。生成した
  SQLは保存または直接実行が可能。他機能からの遷移時、SQLを解析して各タブに反映する
  （リバースエンジニアリング）
- **クエリ保存**: 手入力またはクエリビルダーで作成したSQLに名前を付けて保存。公開
  （Public）/非公開（Private）を選択可能。スキーマを保持しない（実行時に指定）。編集は
  作成者のみ可能。論理的に非表示（retired）にできる
- **クエリ実行**: 読み取り専用SQLのみ実行可能。`:param`形式のパラメータ化クエリに対応し、
  パラメータを自動検出して値設定UIを提供する。実行時に対象スキーマを明示的に指定する
  （許可リスト方式で検証）。SQL、パラメータ、対象スキーマ、結果件数、実行時間、実行回数、
  実行日時、実行者を記録する。保存クエリ実行時は編集不可
- **クエリ履歴**: 実行履歴をページング付きで表示。保存クエリと直接入力クエリを区別。
  実行日時・実行者・対象スキーマ・SQLテキストで絞込可能

### 4.5 監査ログ

#### 必須記録イベント
- **認証イベント**: ログイン、ログアウト、ログイン失敗（日時・ユーザ名。IPアドレス記録は
  未実装）
- **管理操作**: ユーザ招待、ロール変更、ユーザ無効化・再有効化、対象RDBMS接続設定の変更
  （接続の論理削除・再有効化を含む）、スキーマ取り込み操作とその結果、アクセス権限設定の
  変更（グループ変更・権限設定変更・YAMLエクスポート・YAMLインポートを別イベント種別として
  区別）
- **データアクセスイベント**: 大量データ取得（閾値設定可能、デフォルト100件以上）、クエリ
  実行（結果件数・実行時間含む）、データ更新操作（挿入・更新・削除）

#### 仕様
構造化ログ（JSON推奨）として内部データベースに永続化する。記録項目は日時（ISO 8601）、
ユーザID、対象接続ID、操作種別、対象リソース、結果ステータス（IPアドレスの記録は未実装）。
保持期間は「設定可能」を要件とするが、保持期間設定・自動削除（パージ）機能は未実装とする。
security-baseline拡張SECURITY-14により、監査ログはアプリケーションコードから削除・改変
できない構造とする（対象RDBMS接続の論理削除方式（4.2節）とも整合する）。

#### アクセス制御
管理者のみ閲覧可能

## 5. 非機能要件

### 性能・規模
- **同時利用者数**: 約10名を想定
- **大量データ閾値**: 監査ログ対象となるレコード件数の閾値は設定可能（デフォルト100件以上）
- **応答性能**: 典型的なマスタデータ操作に対して妥当な応答性能を確保する（具体的な目標値は
  今回も定めない）

### セキュリティ
- **標準的なWebアプリケーションセキュリティ対策への準拠**: security-baseline拡張
  （SECURITY-01〜15）を全面適用する
- **ログ中の機微情報の扱い**: パスワード・トークン等の機微情報は記録しない
- **アクセス制御が必要な機能の範囲**: 管理機能全般（ユーザ管理、接続設定、権限設定、監査ログ
  閲覧）は管理者限定。データアクセスはアクセス権限モデル（4.2節）に従う
- **未実装として割り切るセキュリティ機能**:
  - 監査ログへのIPアドレス記録
  - ログアウト時のセッション継続時間記録
  - 管理者アカウントのMFA（多要素認証）対応（同時利用者10名規模の社内ツールであり、管理者を
    信頼できる小規模チームで運用する前提のため、文書化された例外として適用除外）

### 可用性・耐障害性
- **可用性の目標**: 特別なSLAは定めない
- **障害時の挙動方針**: 特別なリトライ・フェイルオーバー要件は設けない
  （resiliency-baseline拡張は適用しない）

### デプロイ・運用
- **デプロイ形態**: 3節参照
- **メール送信**: 開発環境ではMailPitコンテナを用いてメール送受信を確認する。本番環境では
  環境変数経由でSMTP設定を構成可能とする
- **監視・ログ**: コンテナ環境に適した構造化ログを出力する。本格的な監視ダッシュボードは
  求めず、ログベースの軽量な検知の仕組み（ログイン失敗・認可失敗等のセキュリティイベント）で
  足りるものとする

### ユーザビリティ
- **対応ブラウザ・デバイス**: デスクトップ利用を中心とし、タブレット等でも大きく崩れない
  程度のレスポンシブ対応を行う（モバイル本格対応は不要）
- **多言語対応**: 初期リリースから日本語＋英語の2言語に対応する。適用範囲は画面文言・
  フォームラベル・エラーメッセージに加え、招待メール・パスワードリセットメール等の通知メール
  文面、監査ログの表示などユーザに見えるテキストすべて。各機能の実装と同時に組み込む。
  言語設定は内部DBにユーザごとに永続化する（3節「UI表示言語」参照）
- **アクセシビリティ**: 特別な準拠基準は定めない

### 保守性・テスト容易性
- **テストカバレッジ方針**: バックエンドはJUnit5 + Mockito、フロントエンドはVitest +
  React Testing Libraryを標準の組み合わせとする
- **property-based-testing拡張の適用有無**: 適用する（全面適用）。権限判定・合成ロジック、
  YAML入出力、SQL生成ロジックを重点対象とする

## 6. ロール・ペルソナ・用語集

### ロール一覧
管理者／一般ユーザの2種類とする。招待時に管理者が設定し、登録完了後も管理者が双方向に
変更できる。

| ロール名 | 概要 | 主要ユースケース |
|---|---|---|
| 管理者 | ユーザ招待・ロール設定・アカウント無効化/再有効化・接続設定・権限設定・監査ログ閲覧を行う | ユーザのメールアドレス登録（招待）とロール設定、RDBMS接続登録、スキーマ取込、権限設定、グループ管理、監査ログ確認 |
| 一般ユーザ | 権限範囲内でマスタデータの閲覧・編集・クエリ実行を行う | 招待メールからの本登録完了、パスワードリセット/変更、データ閲覧・編集、クエリビルダー利用、保存クエリ実行、クエリ履歴閲覧 |

### ペルソナ
- **管理者**: 社内システム管理を兼務する担当者。ユーザの入退社に応じてアカウントを招待・
  無効化し、部署やチームに応じて権限を設定する
- **一般ユーザ**: 普段DBを直接触らない業務担当者。SQLの知識はない、またはクエリビルダーで
  補助されることを前提とする

### 用語集

| 用語 | 定義 |
|---|---|
| 招待 | 管理者がメールアドレスとロールを登録し、招待メールを送信する操作。ユーザはこのメールのリンクから本登録を完了する |
| ロール | ユーザに付与される「管理者」「一般ユーザ」のいずれかの属性。招待時に設定し、登録完了後も管理者が変更できる |
| アカウント無効化 | 管理者がユーザのログインを禁止する操作。再有効化により元に戻せる。ロールとは独立した状態 |
| カスタマイズ定義 | マスタメンテナンス画面の表示・入力を調整するYAML定義（表示ラベル・列順・初期ソート、入力ウィジェット種別、列の非表示・読取専用化、簡易バリデーション）。対象RDBMS接続ごとに持つ。権限モデルを上書きしない |
| 主権限 | スキーマ／テーブル／カラムの各階層に設定する読み書きレベル（NONE/READ/UPDATE）の3値 |
| 補助権限 | スキーマ／テーブル単位に設定するCREATE/DELETEの可否を表す独立した真偽値 |
| 実効権限 | ユーザ個別設定とグループ設定を合成した最終的な権限 |

## 7. 拡張機能（Extensions）設定

| Extension | Enabled | 備考 |
|---|---|---|
| security-baseline | Yes | 管理者MFAのみ文書化された適用除外。SECURITY-01〜15はそれ以外全面適用 |
| resiliency-baseline | No | 同時利用者数10名規模・単独開発・MVPファーストという前提のため |
| property-based-testing | Yes | 全面適用。権限判定・合成ロジック、YAML入出力、SQL生成ロジックを重点対象 |

## 8. 要件確認質問と回答の要約

`aidlc-docs/inception/requirements/requirement-verification-questions.md` で確認した6件の
回答（詳細は本文中の該当箇所に反映済み）:

1. パスワードリセット機能: **必要**（招待と同様のメールリンク方式）→ 4.1節に反映
2. ログイン中ユーザの自己パスワード変更機能: **必要** → 4.1節に反映
3. アカウント無効化機能: **必要**（無効化・再有効化の双方向） → 4.1節に反映
4. ログアウト時のリフレッシュトークン失効: **必要**（サーバ側で即座に失効） → 4.1節に反映
5. RDBMS接続削除時の関連データの扱い: **物理削除を提供せず、論理削除（無効化）のみ**
   → 4.2節に反映
6. UI表示言語設定の永続化方式: **内部DBにユーザごとに永続化** → 3節・5節に反映

## 9. まとめ

MasterMeister5は、既存プロダクトMasterMeister4を踏襲しつつ、招待制ユーザ登録、自前デザイン
システムライブラリの組み込み、外部メールテンプレートエンジンの採用、マスタメンテナンス機能の
YAMLベースカスタマイズを新規に加えた、対象RDBMSのマスタデータ管理・アクセス制御・監査を行う
Webアプリケーションである。security-baseline拡張とproperty-based-testing拡張を全面適用し、
resiliency-baseline拡張は適用しない、同時利用者数10名規模のMVPファースト開発として進める。
